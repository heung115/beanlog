# Single-parent image delta recovery

`image_delta.py` reconstructs complete native OCI/Docker-save image archives from
one verified full baseline and a small encrypted delta. It does not contact GCS,
change IAM, run Docker, start services, or prune backups. The full parent is a
required recovery dependency and must remain retained alongside every dependent
delta. Parent chains are rejected.

Keep full parents and delta baselines in a dedicated baseline download directory,
outside the ordinary daily `backup.pull` retention/prune directory. The current
GCS lifecycle applies only to `beanmap/daily/`; required parents must stay under
the reviewed baseline prefix. This utility does not make an existing generic
local retention policy aware of encrypted parent references.

The first measured candidate contains four patched supporting images: 66 files
reuse verified parent blobs and 19 files occupy 25,433,839 bytes compressed. That
measurement is **not** a bound for the final backup. Later web/API deployments
change image IDs too. Freeze the final eight-service inventory after deployment,
save the required images, and measure the final delta again before testing the
existing storage cap. Duplicate service image IDs are deduplicated; at most eight
reviewed image IDs can be supplied.

## Envelope and trust boundary

The new completed bundle includes fresh database/roles/runtime/config components,
plus `images.delta.tar.gz.age` and `image-base.json.age`. It does not also include
a full image archive. The latter encrypted component contains:

```json
{
  "format": 1,
  "parent": {
    "backup_name": "backup-YYYYMMDDTHHMMSSZ-01234567",
    "image_file": "images.tar.gz.age",
    "ciphertext_bytes": 123,
    "ciphertext_sha256": "<64 lowercase hex characters>",
    "manifest_sha256": "<64 lowercase hex characters>",
    "object_generation": "<exact positive decimal generation>",
    "manifest_generation": "<exact positive decimal generation>"
  },
  "base_archive": {"bytes": 123, "sha256": "<plaintext archive hash>"},
  "delta_archive": {"bytes": 123, "sha256": "<plaintext delta hash>"},
  "expected_image_ids": ["sha256:<reviewed image ID>"],
  "files": {
    "index.json": {"source": "delta", "bytes": 123, "sha256": "<file hash>"},
    "blobs/sha256/<blob hash>": {"source": "base", "bytes": 123, "sha256": "<blob hash>"}
  }
}
```

`--parent-receipt` is an independent local JSON copy of the `parent` object,
populated from the reviewed, exact-generation GCS download. It must not be
generated by trusting the unverified delta envelope itself. The downloader must
pin both object generations and verify the downloaded manifest and ciphertext
against this receipt. `restore_drill.py` checks the local parent's complete
manifest, its exact manifest hash and the image component hash again. Neither
tool claims that a caller-supplied receipt independently authenticates GCS.

Validate the **current** completed bundle with `backup.validate()` before calling
`reconstruct_encrypted()` directly. The restore drill already does this. Age
authentication must reach EOF for metadata, parent and delta before any parsed
image is imported. The independent expected image IDs must come from the reviewed
current runtime inventory, not solely from the delta metadata.

## Build and validate a delta

Use a dedicated owned mode-0700 workspace. Plaintext image archives may include
image configuration and are kept in mode-0600 files only. Library temporary
directories are removed on success and error; explicitly supplied source/output
archives remain the operator's responsibility. The age identity is never copied
into the archive or printed.

Given a fully authenticated plaintext parent and a native candidate archive:

```sh
python3 ops/backup/image_delta.py create \
  --base /private/work/base.tar.gz \
  --candidate /private/work/final-images.tar \
  --delta /private/work/images.delta.tar.gz \
  --reference /private/work/image-base.json \
  --parent-receipt /private/work/parent-receipt.json \
  --expected-image-id sha256:<first-reviewed-ID> \
  --expected-image-id sha256:<next-reviewed-ID> \
  --workspace /private/work
```

If a previously measured small delta is already available, `seal` takes the same
options except `--candidate`. It selects the complete image graph from parent
blobs plus the small delta, validates it, and writes the envelope without moving
the full candidate archive between machines. Top-level `index.json`,
`manifest.json`, and `oci-layout` always come from the delta.

Encrypt the delta and reference separately to the existing dedicated recipient,
then include both ciphertexts in a fresh completed bundle manifest. Never edit a
previously uploaded baseline or skip the full-pool size check. The encrypted
reference and delta are useless if their parent is later removed.

For a standalone local reconstruction, use `reconstruct-encrypted` with `--base`
pointing to the generation-verified parent ciphertext, `--delta` and `--reference`
pointing to the new ciphertexts, plus `--identity`, `--output`, `--parent-receipt`,
the reviewed `--expected-image-id` options, every parent's
`--expected-parent-image-id` from its authenticated runtime inventory, and
`--workspace`. The encrypted recovery API requires these parent IDs independently
and validates the full parent OCI graph before producing the candidate archive.
All output files are
created exclusively: existing files and symlink targets are never overwritten.

## Restore drill integration

The existing authorization flag is still required. For a delta baseline add:

```sh
python3 ops/backup/restore_drill.py \
  --approved-production-restore \
  --bundle /private/download/new-baseline \
  --parent-bundle /private/download/backup-YYYYMMDDTHHMMSSZ-01234567 \
  --parent-receipt /private/work/parent-receipt.json \
  --image-workspace /private/work \
  --expected-delta-image-id sha256:<first-reviewed-ID> \
  --expected-delta-image-id sha256:<next-reviewed-ID> \
  --identity /private/identity.agekey \
  --acl-check-script scripts/verify-function-acls.sql \
  --report /private/work/restore-result.json
```

The drill checks both eight-service inventories. Every changed service image,
including web/API images from later deployments, must be covered by the delta.
It reconstructs and verifies the delta before loading either image set, loads the
full parent to preserve unchanged services, then loads the verified new archive.
Full-baseline restores also verify their entire image graph before import. A
pre-existing Docker image cache cannot substitute for missing archive contents.
Every current runtime image ID must resolve exactly after import. Only the
database starts, with no network or published ports, in disposable volumes.
Database rows, sequences, role/RLS boundaries, function ACLs and a synthetic Vault
roundtrip retain the existing restore checks. Full-service RTO and PITR are not
established by this database-only drill.

## Archive checks and regression coverage

Only three top-level metadata files and `blobs/sha256/<64 lowercase hex>` regular
files are accepted. Optional `blobs` and `blobs/sha256` directory entries are
allowed. Duplicate members, traversal, absolute paths, symlinks, hardlinks,
devices, FIFOs, sparse files and unknown payloads are rejected. PAX and GNU
long-name/long-link headers are rejected before Python's tar parser reads their
extension payloads into memory; the allowed OCI paths fit plain USTAR. Payload counts,
compressed input sizes, expanded outer streams, metadata sizes and decompressed
layer bytes have explicit limits. Layer filesystem contents are never extracted.

Every blob filename, descriptor size/digest, config and ordered layer list is
checked. Gzip/raw OCI and Docker-compatible layer media types are supported;
uncompressed `diff_ids` are verified independently. Native ARM64 children of OCI
or Docker indexes are resolved with a depth bound. Unrecognized platforms,
external descriptors, unrelated blobs and Docker/OCI manifest disagreement stop
reconstruction. Present BuildKit attestations referenced by a native index are
also checked: descriptor/config digests, unknown-platform marker, reference to the
native manifest, bounded JSON documents and raw document diff IDs must agree.
These provenance documents are preserved without executing or trusting their
claims. The four-image real sample uses both OCI and Docker gzip layer
types. New encodings such as zstd deliberately require a reviewed change.

Fresh tar headers are normalized, so the **whole tar** hash may differ from
`docker save`; every OCI member's bytes and content digest remain exact. Native
`docker load` and image-ID inspection are part of the real-data validation.

Run `python3 -m unittest discover -s ops/backup -p 'test_*.py'`. Tests include
malicious outer archives, wrong parent generations/hashes, corrupted or missing
blobs, unexpected images, wrong descriptor sizes, diff IDs and layer ordering,
limits, authenticated-decryption failure, output preservation and later app-image
changes omitted from a proposed delta.

Primary format references: [OCI image layout](https://github.com/opencontainers/image-spec/blob/main/image-layout.md),
[OCI image manifest](https://github.com/opencontainers/image-spec/blob/main/manifest.md),
and [OCI image config/diff IDs](https://github.com/opencontainers/image-spec/blob/main/config.md).
