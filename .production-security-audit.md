# beanmap.site Production Security Audit — 2026-08-27

> Authorized owner assessment. Secret values, IP addresses, account credentials, webhook signatures, and raw exploit payloads are intentionally excluded.

## Executive result

- **No critical or directly internet-exploitable high-severity vulnerability was confirmed.**
- Authentication, row-level authorization, cookie security, network isolation, TLS, secret separation, and production web/API images passed the performed checks.
- One medium-priority webhook replay issue and several low-priority configuration/dependency issues remain. The Caddy finding was remediated on 2026-08-27.
- A wordlist can test only known names and payloads; this report does not claim mathematical coverage of every possible vulnerability.

## Findings

### [MEDIUM] Deployment webhook requests can be replayed

The webhook authenticates the body with HMAC, but does not enforce a timestamp, one-time delivery ID, or replay ledger. On upstream failure, Caddy journal entries contained the request signature header. The deploy poller accepts a requested commit when it is any verified ancestor of the main branch rather than requiring the current head or a monotonic descendant of the deployed commit.

An old valid request could therefore be replayed to cause a temporary rollback to an older, previously successful main commit. The periodic poller would later restore the current head, limiting persistence but not the temporary integrity/availability impact. No replay was performed because it would intentionally roll production back.

Remediation:

1. Rotate the webhook secret. New proxy logs now redact the signature header, but historical journal entries can still contain old signatures.
2. Include a signed timestamp and delivery ID, reject stale requests, and persist consumed delivery IDs.
3. Require the requested commit to equal the current remote main head, or at minimum to be a descendant of the currently deployed commit.
4. Oversized requests now return `413`; retain this behavior in deployment regression tests.

### [REMEDIATED 2026-08-27] Caddy security-maintenance and sandboxing

Production previously used Ubuntu Caddy `2.6.2`, predating the fix for CVE-2026-27589. It now uses the official stable Caddy `2.11.4` package. The admin API moved from TCP `127.0.0.1:2019` to a mode-0600 Unix socket owned by the Caddy service account, and ordinary operator access was verified denied. Runtime config persistence is disabled so the reviewed Caddyfile remains authoritative.

The service now enables no-new-privileges, strict filesystem protection, private devices, protected home/kernel/control/proc views, namespace and address-family restrictions, writable-executable-memory denial, a minimal bind-service capability, and a private runtime directory. `systemd-analyze security` improved to `3.0 OK`. HTTP/3 was disabled because it is unused; HTTP/1.1 and HTTP/2 remain enabled. TRACE/CONNECT return `405` on both protocols, unmatched TLS hosts are aborted, and oversized webhook requests return `413`.

### [LOW] Unused phone authentication is enabled with auto-confirm

Phone signup and phone auto-confirm are both enabled even though no SMS provider is configured and the application uses email authentication. A controlled fictional phone signup did not obtain an account or token; it returned a database constraint error and left no user behind. The path nevertheless expands the authentication surface and discloses an internal database error code through a `500` response.

Remediation: set phone signup and phone auto-confirm to false, then regression-test email signup, login, recovery, and account deletion.

### [LOW] Application pagination can produce an internal `500`

The Go API calculates the SQL offset as `(page - 1) * limit` using an integer. A very large authenticated page value can overflow and cause a `500`. The public web schema caps normal page values, and the Go API is not directly published, reducing impact.

Remediation: reject out-of-range pagination values in the handler before multiplication and add boundary tests.

### [LOW] Unused GraphQL schema is exposed to PostgREST

PostgREST is configured for `public,graphql_public` although GraphQL is not used. The GraphQL entry point currently fails because the extension is disabled, so no data access was obtained.

Remediation: configure only the `public` schema unless GraphQL is intentionally enabled and separately authorized.

### [LOW] Conditional dependency and runtime-tool CVEs

- The Auth binary contains `pgproto3/v2 2.3.3`, affected by CVE-2026-32286. Exploitation requires a malicious or compromised PostgreSQL server to send a malformed protocol message; the database is private and isolated, so this is not directly internet-exploitable.
- Critical/high scanner matches in the PostgREST image belong to an unused ACME test binary (`pebble`), not the PostgREST process.
- Critical/high scanner matches in the PostgreSQL image belong to runtime helper tools (`curl` and `gosu`), not the PostgreSQL server binary.

Remediation: update the Auth dependency when upstream provides a safe migration/fix, and remove unused build/test/helper binaries from final runtime images where possible.

### [LOW] Domain and mail anti-spoofing are monitoring-only

DMARC is `p=none`, SPF uses soft-fail, DNSSEC is absent, and no CAA, MTA-STS, or TLS-RPT record is present. These do not expose the web application directly, but they provide weaker protection against domain/email spoofing and DNS tampering.

Remediation: analyze DMARC reports, then move gradually to `quarantine`/`reject`; evaluate DNSSEC and CAA with the registrar; add MTA-STS/TLS-RPT if mail forwarding supports them.

### [INFO] Additional hardening opportunities

- The production CSP excludes `unsafe-eval` but still permits inline script/style execution.
- Application mutation endpoints have no explicit application-level rate limiter; Auth uses upstream defaults.
- `fail2ban` is inactive, but SSH password and root login are disabled and only public-key authentication is accepted.

## Controls that passed

- **Exposure:** only SSH, HTTP, and HTTPS are internet-reachable; database, application, Supabase gateway, Caddy admin, and deploy webhook listeners are loopback/private.
- **TLS:** valid certificates; TLS 1.0/1.1 rejected; TLS 1.2/1.3 accepted; HTTP and `www` redirect to canonical HTTPS.
- **Caddy:** official stable `2.11.4`; restricted Unix admin socket; strict systemd sandbox; no TCP admin listener or HTTP/3 UDP listener; TRACE/CONNECT consistently rejected.
- **Headers/cookies:** HSTS, CSP, clickjacking, MIME sniffing, referrer, permissions, COOP/CORP, and private/no-store cache controls present. Auth cookie is `HttpOnly`, `Secure`, and `SameSite=Lax`.
- **Authorization:** all nine public tables have RLS enabled. Two disposable users verified that another user could not read, update, or delete the owner's test record, while the owner retained access.
- **Anonymous access:** private tables and mutation RPCs rejected anonymous requests. Unknown tables were not exposed.
- **Secrets:** production keys use non-placeholder values of sufficient length; anon/service keys and database credentials are separated; service-role and PostgreSQL credentials are absent from web/API container environments; API DB URL is mounted as a secret file.
- **Containers:** web and API run non-root with read-only filesystems, all capabilities dropped, no-new-privileges, and CPU/memory/PID limits. Production web, API, and Kong images have no critical/high Docker Scout findings in their active application components.
- **Host:** SSH root/password login disabled; unattended security upgrades active; no reboot required; Docker access is limited to the intended operator account.
- **Discovery:** stable SecLists path/file/API scans exposed no `.env`, VCS metadata, backup, debug, admin, Swagger, or sensitive hidden path. Only the site root and favicon matched. A 5,000-name DNS list and certificate-transparency data found only the root, `www`, and `api`; wildcard DNS is absent.
- **Input fuzzing:** 556 representative payloads across 1,668 local/staging requests produced no injection, traversal, XSS, or authorization bypass; only the pagination overflow above produced a reproducible error.
- **Cleanup:** disposable production users and records were deleted and verified absent after testing.

## Operational observation

One assessment interval overlapped a deployment. The webhook service repeatedly failed with an executable-format error and Caddy returned temporary `502` responses until the binary was corrected. The ordinary application deploy wrapper does not replace this binary, so the event appears to have come from a separate webhook-binary installation/update. Production recovered, the verified main deployment completed, and no container restart loop or OOM condition remained. Atomic binary replacement and a pre-restart executable validation should be added to that separate installation path.
